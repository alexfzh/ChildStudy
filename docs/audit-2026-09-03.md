## 2. 架构设计 (87/100)

### 数据：跨模块耦合图

```
exams.py       → rewards.py              (exam_reward / recalc_subject_rank)
exercises.py   → rewards.py              (get_or_create_achievement / grant_achievement)
exercises.py   → kp_progress.py          (update_kp_progress_on_exercise)
exercises.py   → study_progress.py       (update_progress_on_exercise)
```

### 优势
- **schemas/ 包拆分**（18 文件）+ `__init__.py` re-export，保持 backward-compat
- **routers/question_banks.py 拆分** → question_banks + exercises
- **依赖注入统一**：`Depends(get_db)` / `Depends(get_current_user)` 在 `_PROTECTED` 列表统一注册
- **访问控制 3 层守卫**：`get_current_user` → `require_parent` / `get_accessible_child_ids` → `assert_child_access`
- **避免循环导入**：exercises.py 用函数内 `from routers.study_progress import`（延迟导入）解决 `rewards → exercises` 反向引用

### ⚠️ 架构问题

#### A. exercises.py 是事实上的"业务编排层"
- 5 个 endpoints，但 767 行，**每个 endpoint 都跨 3-4 个 model**
- `submit_exercise` 同时做：批改 → 积分 → 段位 → 成就 → 学习进度 → 知识点进度 → 周报
- 这是 **"fat controller"** 反模式（应该用 service 层）
- 建议：提取 `ExerciseService.submit()` 业务逻辑层

#### B. rewards.py 857 行（最大 router）
- 17 endpoints，但混了：积分计算 / 成就判定 / 段位重算 / 兑换 / 商店 / 排行榜
- `recalc_subject_rank` 是公共函数，被 exams/exercises 双向调用（耦合点）
- 建议：拆为 `rewards_points.py` + `rewards_achievements.py` + `rewards_shop.py`

#### C. 跨模块调用链长
- exercises.submit → rewards.grant_achievement → rewards.check_milestones
- 任何一环失败可能导致部分状态不一致（无分布式事务）
- 现状：靠 SQLAlchemy `commit` 单点提交，无回滚链

## 4. 安全性 (88/100)

### 优势
- ✅ JWT 认证体系完整：`get_current_user` 守卫所有受保护 endpoint
- ✅ `require_parent` 强制家长角色（子账号不能写）
- ✅ `assert_child_access` 防越权访问其他家庭的孩子数据
- ✅ SQL 注入：`_dedupe` 表名走白名单（已修复）
- ✅ login lock 防爆破：5 次失败 → 15 分钟锁定（SQLite 持久化，多 worker 共享）
- ✅ 文件上传：MIME 类型 + 大小双重校验
- ✅ CSV 导入：……**等下，这有问题**

### ⚠️ 安全问题

#### A. CSV 导入无大小限制（P1，已知未修）
- `routers/import_export.py:154, 236`：`await file.read()` 一次读入内存
- **攻击向量**：上传 10GB CSV → OOM 崩溃后端
- 修复：检查 `Content-Length` header 或分块读取

#### B. CORS 通配符（Low）
- `main.py` 默认 `allow_origins=["*"]`
- 仅开发环境可用，生产需收紧到具体域名
- 已在 .env.example 提示，但默认仍是 *

#### C. JWT secret 强度未校验
- `config.py` 接受任意字符串作为 jwt_secret
- 无最低长度要求（256-bit 推荐）
- 攻击向量：弱 secret 可被暴力破解

#### D. SQL 注入修复不完整
- 已修复 `_dedupe`，但其他 f-string SQL 在 migration 函数：
  - `_migrate_exam_paper_analysis`：列名拼接到 `text()` 中（虽然列名来自常量 tuple）
  - `_migrate_child_reward_status`：列名 + DDL 类型拼接
  - 建议：把所有 migration 走 SQLAlchemy `op.add_column()` 风格

#### E. 无审计日志
- 所有写操作（POST/PUT/DELETE）没有 audit trail
- 攻击后无法追溯"谁删了孩子数据"
- 家庭工具场景风险低，但仍属安全短板

## 5. 性能 (72/100)

### 数据
- `element-plus` 938KB（全量打入 chunk）
- `echarts` 541KB（全量打入 chunk）
- 后端 143 endpoints，平均每个 router 5.7 个端点
- SQLite 单文件，最大表 41 个 FK 关联

### 优势
- 全 async 栈（FastAPI + SQLAlchemy 2.0 async + aiosqlite）
- 关系预加载：`selectinload` / `joinedload` 避免 N+1（exercises.py:475 已有实践）
- 分页控制：`limit=Query(200, le=1000)`
- pytest 24.5s 跑完 204 个测试（平均 0.12s/test）

### ⚠️ 性能问题

#### A. 前端 chunk 体积（P2）
- `element-plus` 938KB + `echarts` 541KB = ~1.5MB 一次性下载
- 建议：按需引入（element-plus 支持 unplugin-vue-components 自动 tree-shake）
- 收益：首屏体积可降至 ~300KB

#### B. SQLite 无 WAL 模式（Medium）
- `database.py` 未启用 `PRAGMA journal_mode=WAL`
- 当前并发写场景下，reader 会被 writer 阻塞
- 修复：`PRAGMA journal_mode=WAL; PRAGMA synchronous=NORMAL;`
- 收益：读写并发性能提升 3-5x

#### C. 看板聚合查询未缓存（Medium）
- `dashboard.py` 每次调用都重算"最近 7 天 / 30 天数据"
- 用户每次打开 dashboard 都触发 ~10 次 DB 查询
- 建议：加 `@lru_cache(ttl=300)` 或显式 cache key

#### D. exercises.submit 串行 7 个副作用（Medium）
- 批改 → 积分 → 段位 → 成就 → 学习进度 → 知识点进度 → 周报
- 全是顺序 await，单次提交可能触发 10+ 次 DB write
- 建议：批量化 + 异步任务队列（asyncio.create_task 后台处理非关键路径）

#### E. seed 文件大到吓死人（Low，但影响开发者体验）
- `_seed_phase67.py` 39KB, `_seed_english_2026_edition.py` 39KB, `_seed_math_questions.py` 31KB
- 单文件 600+ 行 JSON 拼接
- 建议：拆分到 `seeds/data/*.json` 文件 + 加载器

## 6. 数据库设计 (90/100)

### 数据
- 36 个 model，41 个 ForeignKey
- 表名规范：snake_case 复数（如 `child_ranks`, `wrong_questions`）
- 已配置：`PRAGMA foreign_keys=ON`（在数据库初始化时）

### 优势
- ✅ 外键级联删除合理（`ondelete="CASCADE"` / `SET NULL`）
- ✅ 复合索引齐全：`Index("ix_users_family_role", "family_id", "role")`
- ✅ `__table_args__` 中显式 Index（如 exam 的 `(child_id, exam_date)`）
- ✅ 枚举值通过 `pattern=` 约束（pydantic 层面）
- ✅ 软删除用 `is_active` 而非真删（question_banks）

### ⚠️ 不足

#### A. 无 DB 迁移工具（Medium）
- 所有 schema 变更通过 `_migrate_*` 函数散落在 `database.py`
- 已有 11 个 migration 函数（auth foundation / exam paper analysis / exercise time spent / ...）
- 风险：迁移顺序靠注释和函数名排序，无原子性
- 建议：迁移到 Alembic（行业标准）

#### B. 无 unique 约束在数据层
- 例如 `User.username` 唯一性靠应用层校验
- 数据库级别没加 `UNIQUE` 约束（除了 username）
- 并发场景下可能插入重复数据

#### C. `JSON` 字段无结构约束
- `exam.questions` / `exercise.questions` 是 JSON 字段
- 业务逻辑嵌套依赖 JSON 结构，但 schema 漂移无保护
- 风险：老数据格式与新代码不兼容

#### D. `PeriodicReport` 表无 `__tablename__`
- 模型定义存在但表名缺失（独立审计发现）
- 这会导致 `Base.metadata.create_all` 时跳过该表

## 7. 应用体验 (88/100)

### 数据
- 23 个前端 view，22 个有 try/catch（96%）
- API 拦截器统一处理 401 / 跳登录（api/index.js）
- 路由守卫：访问受保护页面 → 检查 token → 跳 /login

### 优势
- ✅ 401 自动跳登录（不弹错，router guard 处理）
- ✅ 22/23 view 有 try/catch（fail-fast UX）
- ✅ Element Plus 提供统一组件风格
- ✅ dayjs 时间处理统一（无 moment.js 包袱）
- ✅ localStorage 缓存 token + user + accessible_child_ids（避免每次刷新重拉）

### ⚠️ UX 问题

#### A. 错误提示用 ElMessage 但无统一文案库（Medium）
- 各 view 自己 `ElMessage.error('加载失败')`，文案风格不统一
- 用户看不到具体原因（422 字段错误不展示后端 message）
- 建议：统一 `useApiError` composable

#### B. Loading 状态不一致（Low）
- 部分 view 用 `loading.value = true`，部分用 element-plus 的 `v-loading`
- 用户体验：某些按钮点击后没反应（loading 没显示）
- 建议：统一 loading 模式

#### C. 无全局错误边界（Low）
- Vue 组件错误无兜底页（除非用户主动刷新）
- 任意 view 抛错 → 整个 app 空白
- 建议：`errorCaptured` 钩子 + 全局 fallback

#### D. 无空状态设计审计
- 部分 view 没数据时显示 "暂无数据" 文字 + emoji
- 部分 view 显示空白页
- 建议：统一 `<EmptyState>` 组件

#### E. 移动端适配未审计
- ECharts 在窄屏可能溢出
- Element Plus 桌面端优先，移动端需要单独测试

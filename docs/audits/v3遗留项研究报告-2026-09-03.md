## P1 详析

### 1️⃣ N+1 查询 — 实测 18 处,热路径 8 处

自研扫描脚本(循环体内直接 `await db.execute/get/scalar`)实测结果,分两类:

**A. 读路径热端点(值得修,8 处)**

| 位置 | 场景 | 影响 |
|---|---|---|
| `kp_unit.py:78,96,99,105` | KP-Unit关联列表逐条查 | 管理页列表几十条,真实 N+1 |
| `question_kp.py:80,97,101,108` | 题库-KP关联逐条查 | 同上 |
| `kp_progress.py:120,253,257` | 学习进度循环查 | 学生高频访问页 |
| `study_progress.py:90` | 循环查 unit_qids | 进度页 |
| `rewards.py:457` | 循环查 latest | 段位链路 |
| `exercises.py:78` | 循环 LIKE 匹配候选题 | 练习页 |
| `dashboard.py:116` | compare_children 每孩子查 exams | 仅2孩子,影响小 |

**B. 写路径低频(可不修,5 处)**:`import_export.py:188,285`(CSV导入,已有 `max_import_rows` 上限)、`exercises.py:315,338`(创建时校验,低频)

**影响评估**:家庭数据量(百~千条)下 N≈几十、SQLite 本地 ~1ms/查询,单端点多耗几十 ms——真实但不致命;数据量上万或经 LAN/公网远端访问时劣化明显。

**修法**:统一模式为「循环外一次 `IN` 批量预取建 `dict` 映射,循环内查内存」,比 `selectinload` 更直接(这批代码是手工 join 而非 relationship 懒加载)。

**成本**:8 处热路径约 2-3 小时(含回归测试)。

### 3️⃣ element-plus 全量打包 — 确认,938KB

**证据**:
- `main.js:3,31` `import ElementPlus` + `app.use(ElementPlus)` 全量注册所有组件
- `main.js:8` 全量 CSS `element-plus/dist/index.css`
- 实测 `dist/assets/element-CtD2lhiJ.js` = **938,904 字节**(与 v3 数字一致)

**方案**:`unplugin-auto-import` + `unplugin-vue-components`(配 `ElementPlusResolver`),移除全量 `app.use`。已验证兼容性:
- ✓ `ElMessage` 等 API 已是 21 处显式按需导入,与方案兼容
- ⚠ **风险点**:`zhCn` locale 目前靠 `app.use(ElementPlus, { locale })` 传递,按需化后需改用 `<el-config-provider :locale="zhCn">` 包裹 `App.vue`,漏改会导致日期选择器等变英文

**预期收益**:element JS chunk 938KB → 约 250KB,gzip 约 301KB → 约 80KB;首屏(尤其移动端)明显加快。

**成本**:1-2 小时(改 vite.config + main.js + App.vue,build 后全页冒烟)。

### 4️⃣ CI — 比 v3 说的更严重:**现有 CI 必挂(真 bug)**

v3 只说"缺跨平台/缺 audit step",实测发现更根本的问题:

```
ci.yml:22  .venv/bin/pip install -r requirements.txt
ci.yml:24  .venv/bin/ruff check .        ← ruff 在 requirements-dev.txt,未安装!
ci.yml:26  .venv/bin/python -m pytest    ← pytest 同样未安装!
```

`ruff`/`pytest`/`pytest-asyncio`/`httpx` 全在 `requirements-dev.txt`,CI 只装了生产依赖 → **首次运行 lint/pytest 步骤必失败**。此 CI 从未真正跑通过(当前 repo 尚未 push 触发)。

**完整修复方案**:
1. 安装命令改为 `-r requirements.txt -r requirements-dev.txt`
2. 补 `npm run build` + `npm run audit:routes`(脚本已确认存在:`frontend/scripts/audit-routes.py`)
3. 补 `python backend/scripts/audit-schema-router.py`(脚本已确认存在)
4. 跨平台:`matrix: [ubuntu-latest, windows-latest]`;⚠ Windows 下 `.venv/bin/` 是 `.venv/Scripts/`,统一改用 `python -m ruff` / `python -m pytest` 规避路径差异
5. audit:routes 用 python,需 CI 装好 python 后再跑(与后端 job 合并或复用 setup-python)

**成本**:45 分钟(含验证:本地模拟 Linux 路径改动无法完全验证,首次 push 后观察一次运行)。

## P2 详析

### 5️⃣ models.py 拆分 — 确认 37 模型/759 行/41KB

实测 37 个模型(v3 报 36,差额为新增的 `RevokedToken`)。自然域分组清晰:

```
models/
  __init__.py        ← re-export 全部 37 个,外部 `from models import X` 零改动
  child.py           (Child, GradeHistory, Family, User)
  learning.py        (Exam, ExamQuestion, Homework, Timeline, GrowthRecord, ...)
  rewards.py         (Reward, ChildReward, Achievement, ChildAchievement, PointsLog, ChildRank)
  question_bank.py   (QuestionBank, Question, Exercise, KnowledgePoint, QuestionKnowledgePoint, ...)
  textbook.py        (TextbookVersion, TextbookUnit, QuestionUnit, KnowledgePointUnit, StudyProgress, ...)
  system.py          (AIReport, PeriodicReport, Quote, LoginLock, RevokedToken, ProjectWork, ...)
```

**风险评估:低**。`models/__init__.py` re-export 后全部现有 import 点(`from models import Child, ...`)无需改动;FK/relationship 引用改为模块内 import 即可;ruff+214 测试兜底。

**收益**:可读性↑、git diff 噪声↓、按域定位快。**纯工程债,不影响功能**。
**建议**:可做可不做;若做,2 小时。适合与 Service 层拆分同批做(一次大重构)。

### 6️⃣ rewards.py(879行/26函数)/ exercises.py(767行/7函数)拆 Service 层

实测结构:
- `rewards.py` 五大块边界清晰:段位 / 积分 / 考试奖励编排 / 商城兑换 / 成就 CRUD——拆 `services/reward_service.py` + `rank_service.py` + `achievement_service.py` 是自然的
- `exercises.py` 恰恰相反:只有 7 个函数,是**超长函数**问题(单函数上百行),拆 Service 收益不如先拆函数

**判断**:认同 v3 的"边际收益中等、难拆干净",且 `grant_exam_reward` 已被 `exams.py` 跨模块复用,现有分层边界尚可接受。
**建议**:**缓**。触发条件:下次给 rewards/exercises 加新功能时顺势拆,不单独投入。若届时做,连带把 models 拆包一起做。

### 7️⃣ 前端 JS→TS — 实测 0 TS(32 vue + 6 js = 38 文件)

实测比 v3 估的"48+ 文件"少,但结论不变:

| 方案 | 内容 | 成本 | 判断 |
|---|---|---|---|
| C. 全量迁移 | 38 文件重写 + 类型 | 40-80 小时 | ❌ 不值,家庭工具收益低 |
| B. 渐进(可选) | `tsconfig` allowJs + **仅给 `src/api/index.js` 和 Pinia store 加 TS/类型**;新文件一律 TS | 半天 | ⭕ 可选;后端 schemas.py 是 Pydantic 强类型,API 层对齐后能挡住大部分前后端契约 bug |
| A. 维持现状 | 不动 | 0 | ✓ 默认 |

**建议**:默认 A。若你常遇到"接口返回字段名对不上"类 bug,选 B(半天);全量 C 不建议。

**必做**:CI 修复(有真 bug,45 分钟,1+2+3 合并一次做)。
